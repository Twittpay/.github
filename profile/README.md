## What is TwittPay?

TwittPay is a Bangladesh-focused payment gateway built for merchants who want to take mobile financial service (MFS) payments without a bank-issued merchant account. A small reader app on your phone forwards incoming payment SMS to TwittPay. The moment a customer pays, TwittPay matches the SMS to the order and marks it paid, with no manual checking.

You create a **Brand**, copy its **Brand Key**, install an addon for your platform, and you are live. The customer pays on the hosted TwittPay checkout page and is sent straight back to your site.

## How it works

1. **Create a brand** in your TwittPay dashboard and copy the Brand Key.
2. **Install an addon** for your platform from the list below and paste the Brand Key.
3. **Customer checks out.** Your site creates a payment and sends the customer to the TwittPay checkout.
4. **Customer pays** with bKash, Nagad, Rocket, a bank or crypto.
5. **TwittPay verifies** the payment from the SMS the instant it arrives.
6. **Your site re-verifies** on the server and marks the order or invoice paid exactly once.

## Features

### Payments and checkout
- Hosted checkout page, compact and responsive on mobile and desktop
- **Invoices** and shareable **payment links** from the dashboard, no website needed
- Customer name, email and amount captured on every payment
- Automatic redirect back to your site after payment
- USD to BDT conversion with a rate you control
- Per-brand checkout: enabled gateways, support contacts, Tax ID and website card all come from the brand
- Checkout **Support** and **Details** panels with Telegram contact, Tax ID and a verified-website badge
- Pending-payment handling, so a payment approved later still completes the order

### Supported payment methods
- **Mobile wallets:** bKash, Nagad, Rocket, Upay, SureCash, Cellfin, Tap, iPay, OK Wallet, mCash, MYCash
- **Account types:** Personal, Agent and Merchant for bKash, Nagad and Rocket. Merchant accounts can use the wallet's API or the same SMS verification
- **Banks:** Islami Bank (IBBL / CellFin), City Bank, Eastern Bank, Prime Bank, Pubali Bank, UCB, Dutch-Bangla Bank, BRAC Bank, with generic SMS parsing for more
- **International and crypto:** Binance Personal (Binance Pay API) and Cryptomus
- **Manual bank flow:** automatic check, then Transaction ID, then payment-slip upload for merchant review
- Multiple instances of the same gateway under one brand, each with its own display name

### Real-time SMS verification engine
- The reader app pushes each SMS to the server the second it arrives. Verification is instant, with no artificial delay
- **Three-layer matching:** full number, then last 3 digits, then last 2 digits, always together with the amount
- **Transaction ID fallback:** the customer can type or paste a TxnID and it verifies in the background, with no extra button
- **Rocket, MYCash and mCash** use a 12-digit account number for exact matching
- **Conflict protection:** if two customers pay the same amount at the same moment, auto-matching stops and both are asked for a TxnID, so a wrong payment never passes
- **Claim lock:** once an SMS matches a payment it is locked and can never be used for another
- Unique extra amount for bank payments so each transfer can be matched safely
- One shared sender list for wallets and banks, so adding a new bank needs no per-bank code

### Automatic completion and notifications
- A single cron run verifies and completes payments even if the customer never returns to the page
- The customer gets a "your invoice is paid" email when the cron completes it
- TwittPay notifies your website so the service is delivered, and the invoice link shows as paid
- In-app notifications and email for important account events

### Anti-fraud and security
- Anti-skip protection: a hand-typed success URL can never mark a payment as paid
- Server-side re-verification in every addon, and idempotent success handling so an order is marked paid only once
- Duplicate-transaction guards on every gateway
- **Domain verification** with a DNS TXT record and a server IP allow-list
- **DomainGuard:** a brand with no verified domain and no allowed server IP cannot process live payments
- Brand Keys are masked in the dashboard with Show and Copy, and are never placed in browser JavaScript
- CSRF protection on all forms
- Platform brand protection: the platform's own brand cannot be deleted or deactivated

### Brands, domains and vendors
- Multiple brands per account, each with its own gateways, checkout and contact details
- One domain can serve several brands of the same owner
- **Vendor sharing:** a domain owner shares a secret code and vendors connect their own brands to the domain
- A vendor on a different server can add their own server IP, otherwise the default is used
- The domain owner's server IP is never shown to normal merchants
- Secret codes stay visible to the owner, masked, and a new code instantly retires the old one

### Devices: Android and iOS
- **Android reader app** (`com.twittpay.app`): forwards payment SMS, keeps a filterable SMS log, supports Android 15 edge-to-edge
- **iPhone support** through Apple Shortcuts, with a separate SMS-only key for iOS
- One **Devices** page: a single "Connect New Device" button, one table, QR codes that open in a popup
- Device keys carry a platform prefix (`and_` or `ios_`)
- Android and iOS share the device limit of your plan
- Setup guides for Android and iOS in the documentation

### Merchant dashboard
- Invoices, payment links, customers, brands, devices, gateways and transactions in one panel
- Customers feature: add, edit and reuse customers on invoices
- Activity log, profile and avatar settings
- Plans with offer pricing, strikethrough prices and discount badges
- Clean, responsive interface with a redesigned sidebar

### Developer experience
- Simple REST API: create a payment, verify a payment
- `API-KEY` header authentication
- Webhook support with server-side re-verification
- Full developer documentation inside the dashboard
- Verify responses carry your own metadata back, so you can bind a payment to your order or invoice securely
- Retry with backoff for temporary network failures in the WHMCS module

### Legal and trust
- Terms and Conditions and Privacy Policy pages
- SMS data is kept only briefly and then removed automatically
- Google Play compliant SMS permission disclosure for the Android app
- Hosted on SatisfyCloud infrastructure with Cloudflare in front

## Quick API example

```bash
curl -X POST https://checkout.twittpay.com/api/payment/create \
  -H "API-KEY: YOUR_BRAND_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "cus_name": "John Doe",
    "cus_email": "john@example.com",
    "amount": "500",
    "success_url": "https://yoursite.com/success",
    "cancel_url": "https://yoursite.com/cancel",
    "metadata": { "order_id": "1001" }
  }'
```

The response contains a `payment_url`. Send the customer there. After they return, confirm the payment on your server:

```bash
curl -X POST https://checkout.twittpay.com/api/payment/verify \
  -H "API-KEY: YOUR_BRAND_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "transaction_id": "TRANSACTION_ID" }'
```

Only mark the order paid after verify confirms it, and only once. Never put the Brand Key in browser code.

## Good to know

- **One key is enough.** An addon needs only the Brand Key. There is nothing else to configure.
- **Currency.** Payments are in BDT. If your store uses USD, set the USD to BDT rate in the addon.
- **Several shops, one account.** Use a separate Brand Key per store, department or vendor.
- **Updating.** Download the newest zip from the repository's Releases page and replace the old files.
